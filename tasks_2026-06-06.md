# Tasks — 2026-06-06: Agents become HTTP(S) clients; DB is server-only

Progress markers: `[x]` done · `[ ]` pending · `[~]` in progress

## Why

A supervisor-spawned (template/co-located) agent logs
`no provider available for roles [orchestrator] — pausing task pickup` forever.

Root cause: `workflow/agent_supervisor.go:288` launches the agent **without `--config`**.
In `main.go:386` the LLM executor is only wired when `configPath != ""`, so the spawned agent
runs in polling-only mode with `a.executor == nil`. The poll-loop guard (`agent/agent.go:273`
→ `canRun := a.executor != nil && a.executor.CanExecute(...)`) is then always false. The
provider shown in the UI lives in the **server's** registry; the agent never sees it because it
loaded no config/DB. It is not a provider-matching bug — the matching code never runs.

## Decisions (confirmed)

- **DB is server-only.** Agents never open the database; all data access is over HTTP(S).
- **Secrets over the wire.** Agents need provider **API keys** to call the LLM, so the channel
  must be secure: **HTTPS** + optional **token auth**.
- **HTTPS by default.** The server serves HTTPS by default. A single **`insecure` config flag**
  (e.g. `server.insecure: true`) switches it to plain HTTP for local/dev use.
- **TLS cert = provided-else-auto.** In HTTPS mode use cert/key paths from config when set;
  otherwise the server auto-generates and persists a self-signed cert.
- **Dedicated agent vs UI endpoints.** Agent traffic uses a **dedicated namespace `/api/agent/*`**
  gated by `agents.api_key`; the browser **UI keeps `/api/*` with no key**. The agent key is
  **never** sent to the browser (embedding a key in the served page is unsafe — anyone who can
  load the dashboard could read it). Endpoints both sides use (task results, comments, context,
  logs) get an agent-namespaced route that shares the same handler logic as the UI route; only
  the path + middleware differ. Provider **secrets** live only under the agent namespace.
- **Auth is config-driven.** If `agents.api_key` is set, every `/api/agent/*` route requires that
  bearer key (any origin — no loopback exception). If unset, the agent namespace is open. UI
  routes are unauthenticated for now; a session-based UI login is **future work, out of scope.**
- **All agent types behave identically.** No co-located/remote special-casing in logic. Every
  agent resolves its connection settings (server URL, auth token, TLS trust) from **env and/or
  config**; co-located agents simply receive those via env from the supervisor.
- **Missing-connection abort.** If the server requires a key and the agent has none (no env, no
  config) → the agent **aborts at startup** with a clear "agent API key required (set it in
  config or via env)" error rather than starting unauthenticated. In practice this is the
  "remote agent started with no config" case.
- **Config precedence (data).** `--config` optional. With config and no flag → use config. With
  config and `--server-override` → server values override config **in memory only** (the file on
  disk is never modified). With **no config** → fetch all data (providers/roles) from the server.
- **Import cycle.** Resolved with a `ToolBackend` interface defined in `tools` (idiomatic Go;
  see T6). Not a redesign.

## Success criteria

1. A co-located agent started with only `--server` (no `--config`) wires its executor, resolves
   its roles to a provider over HTTPS, and picks up tasks.
2. `agent` and `tools` packages no longer receive `*db.Database`; no `db.Open` on the agent path.
3. Agent traffic is confined to `/api/agent/*`; when `agents.api_key` is set those routes require
   the bearer key (the secret provider endpoint always behind it), while the browser UI on
   `/api/*` needs no key and never receives one.
4. Backend `go test ./...` green, coverage ≥ 80% on changed packages; UI `pnpm test` green.

## T1 — HTTPS transport (default on; `insecure` flag for HTTP)  `[x]`

- Serve the API over **TLS by default**. Config: `server.tls.cert_file` / `server.tls.key_file`.
  If both set → use them. Else → generate a self-signed cert (localhost + 127.0.0.1 SANs),
  persist to `storage.root` (e.g. `tls/server.crt`,`server.key`) and reuse on restart.
- `http.Server` → `ListenAndServeTLS` normally; `server.insecure: true` (single flag) serves
  plain HTTP instead (local/dev).
- Agent side: when the server URL is `https://`, the agent verifies the cert against a CA it
  trusts (CA path from config for remote; cert handed via env for co-located). An agent-side
  `insecure` option may skip verification for dev only (default = verify).

Files: `config/`, `main.go` (server start + `--insecure`), `server/server.go` (a `tls.go` helper).
Tests: cert helper generates a valid, parseable self-signed cert with expected SANs; provided
paths take precedence over auto; `insecure` serves HTTP.

## T2 — Dedicated agent namespace `/api/agent/*` + token auth  `[x]`

- **Agent subrouter.** Mount all agent-initiated routes under `/api/agent/*` with an auth
  middleware. The UI's existing `/api/*` routes are untouched (no key). Shared operations reuse
  the same handler functions under both paths.
- Agent routes to mount under `/api/agent/` (migrate the `ServerClient`, T4):
  register, heartbeat, offline, tasks/next, task result, submit-for-review, reviews,
  pull-request decisions, comments, context save/query, logs, skills, roles,
  `internal/providers`, and the planning endpoints (T5).
- **Token source:** `agents.api_key` from config (optional). Unset → namespace open. Set → the
  required bearer token. The supervisor reads the same value to inject into co-located children
  (T8); the browser never receives it.
- **Middleware:** when `agents.api_key` is set, require `Authorization: Bearer <key>` on every
  `/api/agent/*` route, any origin. No loopback exception, no UI involvement.
- New `GET /api/agent/internal/providers` → full `[]*db.Provider` **with** `APIKey` + `Models`
  (agent-namespace + token-gated; this is the only place secrets leave the server).

Files: `server/handlers.go` / new `server/agent_routes.go` (subrouter + middleware), `config/`.
(No UI changes — the dashboard does not authenticate.)
Tests: key unset → `/api/agent/*` open; key set → 401 without/bad token, 200 with token;
UI `/api/*` routes never require a key; `/api/agent/internal/providers` returns keys with a valid
token; a shared op (e.g. comments) works under both the UI and agent paths.

## T10 — Git over HTTPS  `[x]`

HTTPS-by-default broke the agent's git clone (repo URL was hardcoded `http://`, and
go-git's transport didn't trust the self-signed cert → `400 / HTTP request to an HTTPS server`).

- `server/claim.go`: repo URL scheme is `https` unless `server.insecure` (then `http`).
- `agent/git_tls.go`: `InstallGitTLS(*tls.Config)` installs a go-git HTTPS transport using the
  same TLS config as the API client; called from `buildAgent`. `agentTLSConfig` now layers the
  server CA on system roots so external HTTPS still verifies.

## BUGFIX — queue supervisor planner role  `[x]`

`workflow/queue_supervisor.go` hardcoded `Role: "planner"` (a name, unresolved) for auto-queue

## Risks / open decisions

- **UI over HTTPS — resolved.** HTTPS is default; the self-signed dashboard shows a browser
  warning unless the cert is trusted. For local/dev, set `server.insecure: true` to serve HTTP.
- **Auth scope — resolved.** Dedicated namespaces: agent traffic on `/api/agent/*` (gated by
  `agents.api_key` when set), UI on `/api/*` (no key). The agent key is never sent to the
  browser. A UI session-login is future work, out of scope.
- **Remote cert trust.** Remote agents must trust the (possibly self-signed) server cert via a
  configured CA bundle (or an agent-side `insecure` skip for dev). With a real CA cert (provided
  mode) this is automatic.
- **docker-compose agents.** They currently load providers from their own config/DB. Under the
  new precedence they keep working *with* `--config` and no override; confirm that's the intended
  default for those deployments.
- **`get_next_task` tool semantics.** Overlaps the agent's own polling; confirm the target
  endpoint so orchestrator-driven dequeues behave as before.
- **Transport.** HTTPS now; gRPC noted as a possible future swap — out of scope.

## F6 — Full cost metrics with attribution  `[x]`  (implemented in stages A–D)

**Current state.** The `metrics` table (`migrations.go:133`) records **agent/task** LLM calls
only: `task_id, agent_id, model, tokens, cost, success`. Chat usage lives in a *different* table
(`messages`: `tokens_used/input/output/duration`, joined to `conversations.provider_id`) and
records **tokens but no cost**. So chats are invisible to cost metrics, and there is no
agent-vs-chat / agent-type / per-agent breakdown.

**Proposed design — make `metrics` the single cost ledger for every LLM interaction.**

1. Migration adds attribution columns to `metrics`:
   `source TEXT NOT NULL DEFAULT 'agent'` (`agent`|`chat`), `provider_id TEXT`,
   `agent_role TEXT` (the agent "type": worker/reviewer/orchestrator), `conversation_id TEXT`,
   `project_id TEXT`. (Keep existing rows valid via the default.)
2. Write one `metrics` row per completion:
   - **Agent executor** (already records cost) → set `source='agent'`, `agent_id`, `agent_role`,
     `task_id`, `project_id`, `provider_id`, `model`.
   - **Chat** (`handleLLMChat`) and **project-detail chat** (`project_chat_handler.go`) →
     set `source='chat'`, `conversation_id`, `project_id` (when the chat is project-scoped),
     `provider_id`, `model`, and **compute cost** from the provider model pricing
     (`ProviderModel.InputPerMillion/OutputPerMillion` already exist).
3. Query endpoint: `GET /api/metrics/costs?group_by=<dim>&from=&to=` where `dim` ∈
   `{source, agent_role, agent_id, provider, model, project, day}`, returning
   `[{key, input_tokens, output_tokens, cost, count}]`. (Extends the existing
   `/api/metrics/costs` handler.)
4. UI — a "Cost breakdown" added to the **Providers page metrics section** (same section as the
   merged cost box from F5) with a group-by selector: **Agent vs Chat**, **By agent type**,
   **By specific agent**, **By provider/model**, plus a table and a small bar chart. Date-range
   filter optional. (No new page/nav entry.)

**History.** Attribution is **from now on only** — existing `messages` rows are not backfilled;
no historical cost rows are synthesized. (Tokens already recorded stay visible where they are.)

**Lighter alternative** (note, not recommended): leave `messages` as-is and `UNION` chat usage
into cost queries at read time. Less migration, but cost must be recomputed on every query and
the two sources stay schema-divergent. The unified ledger (above) is cleaner and is the
recommendation.

Files: `db/migrations.go`, `db/logs.go` (Metric model + `CreateMetric` + new grouped query),
`db/models.go` (Metric struct fields), `agent/executor.go` (populate new fields),
`server/llm_handler.go` + `server/project_chat_handler.go` (write chat metrics),
`server/handlers.go` (metrics/costs `group_by`), `ui` metrics view + `api.js`.
Tests: Go — chat completion writes a `metrics` row with computed cost; `group_by` aggregation
returns correct sums per dimension; agent rows carry `agent_role`. UI — breakdown renders and
switches dimensions.
