## Bug 1 — Log timestamps show time only, no date

**[x] Fix log timestamp display across all log views**

### Problem
All three log views call `toLocaleTimeString()` which omits the date.
On a server that runs for more than a day, entries from yesterday look
identical to entries from today.

### What to do
Replace every `toLocaleTimeString()` call in the log-rendering code with
a combined date + time format. Use a single shared helper so the format is
consistent everywhere.

Suggested format: `toLocaleString([], { month: 'short', day: 'numeric', hour: '2-digit', minute: '2-digit', second: '2-digit' })`
— matches the style already used on the reviews section of TaskDetail.

### Files to touch
- `ui/src/pages/Agents.svelte` — line ~305: `new Date(l.timestamp).toLocaleTimeString()`
- `ui/src/pages/Logs.svelte` — `formatTime()` function (~line 126): returns `toLocaleTimeString()`
- `ui/src/pages/TaskDetail.svelte` — the `loadLogs` section renders log timestamps via `formatTime` inherited from the same pattern; confirm no separate instance exists

Consider extracting a shared `formatTimestamp(ts)` helper into
`ui/src/lib/time.js` (create if it doesn't exist) and importing it in
all three pages.

### Tests
- Vitest unit test for the `formatTimestamp` helper: verify a timestamp from
  a previous day includes the date portion in the output string.

## Bug 2 — Queue button does not work; queued tasks show no indicator

### Problem
Two related issues in the same flow:

1. **Queue button has no effect.**
   In `Tasks.svelte` the Queue button calls `setStatus(t.id, 'BACKLOG')`,
   which sets the task back to `BACKLOG` — not into a queued state.
   There is no call to a `queueTask` API function.
   `api.js` exports `unqueueTask` (`POST /api/tasks/:id/unqueue`) but there
   is no corresponding `queueTask` export.
   Check whether `POST /api/tasks/:id/queue` exists on the server; if it
   does, add `queueTask` to `api.js` and wire it to the button.

2. **No visual indicator for queued tasks.**
   `statusColors` in `Tasks.svelte` has a `task_queued` entry (line 61) but
   the status badge renders `t.status` directly (line 504). If the server
   returns a status value like `QUEUED` the badge will fall through to the
   grey default because the key in `statusColors` is `task_queued`, not
   `QUEUED`. Align the key names with actual server-returned status strings.

### What to do
1. Check the server-side task status values (`db` package / task model) and
   confirm the exact string returned for a queued task.
2. Add `export const queueTask = (id) => post(\`/api/tasks/${id}/queue\`)` to
   `ui/src/lib/api.js` (or wherever the api helpers live).
3. In `Tasks.svelte`: replace the Queue button's `setStatus(t.id, 'BACKLOG')`
   call with `queueTask(t.id)`.
4. In `TaskDetail.svelte`: `handleQueue` also calls
   `updateTask(taskId, { status: 'BACKLOG' })` — replace with `queueTask`.
5. Fix the `statusColors` map keys (both `Tasks.svelte` and `TaskDetail.svelte`)
   to use the real server status strings so the indicator renders correctly.

### Files to touch
- `ui/src/lib/api.js` (or `ui/src/api.js`) — add `queueTask`
- `ui/src/pages/Tasks.svelte` — Queue button handler + statusColors keys
- `ui/src/pages/TaskDetail.svelte` — `handleQueue` + statusColors keys

## Bug 3 — Task detail page shakes due to unnecessary re-renders

**[x] Eliminate UI shake caused by full reload polling on TaskDetail**

### Problem
`TaskDetail.svelte` runs a `setInterval` every 5 seconds that calls
`loadLogs(taskId)` (line 334). `loadLogs` replaces the `logs` array
reference on every tick even when the server returns the same data.
Svelte re-renders the log list, causing visible layout shift / shaking.

Additionally, `loadAll()` fetches the task, all links, dependencies,
checklist items, comments, transitions, reviews, project data, and logs
in one burst. If this is ever called from a refresh path, all sections
re-render at once.

### What to do
1. **Deduplicate log updates.** In `loadLogs`, compare the incoming list
   against the current `logs` state before assigning. Only assign if the
   content has changed (compare by serialising to JSON or by checking the
   last entry's `id`/`timestamp`).
   ```js
   // example guard
   const incoming = await fetchLogs(...)
   if (JSON.stringify(incoming) !== JSON.stringify(logs)) {
     logs = incoming
   }
   ```
2. **Separate the polling concern from full data load.**
   The poll timer should only refresh data that actually changes frequently
   (logs, task status). Heavy secondary data (comments, checklist, reviews,
   transitions, dependencies) should not be fetched every 5 seconds.
   Split `loadAll` into a lightweight `pollTask()` that fetches only
   `/api/tasks/:id` + `/api/logs` and a full `loadAll()` called only on
   initial mount.
3. **Guard task assignment the same way.** Only reassign `task = t` if the
   fetched task differs from the current value (compare `updated_at` or
   the full JSON). This prevents reactive sections from re-rendering when
   nothing changed.

### Files to touch
- `ui/src/pages/TaskDetail.svelte`
  - `loadLogs()` function
  - `loadAll()` function — split into initial load + poll
  - `onMount` interval setup

### Tests
- Vitest: mock the fetch; assert that assigning `logs` is skipped when the
  server returns the same payload twice in a row.
- Vitest: assert that the polling interval only calls the lightweight poll
  function, not `loadAll`.
