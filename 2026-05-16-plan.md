# Plan — 2026-05-16

Progress markers: `[x]` done · `[ ]` pending · `[~]` in progress

Open assumptions confirmed up front (so the rest of the plan is concrete):
- Task progress checklist: per-task editable items, with a separate "templates" facility on Settings so projects/tasks can adopt a default set. "Iteration groups" = labelled re-runs of the same checklist (e.g. attempt 1, attempt 2 after review failure).
- Chat streaming: stream where the provider supports it natively (Ollama, OpenAI); other providers continue returning whole-message replies. WebSocket gets a new `chat_chunk` envelope.
- Task dependencies: soft warning. UI lists deps and shows a warning on the task and in logs when an agent claims/works a task with un-completed deps. No scheduler blocking.
- Playwright: full regression. Smoke per page + feature coverage + regression tests for every bug fixed in this plan. New `ui/tests/e2e/` directory; new Taskfile target.

### A6. [x] Playwright tests — full regression
Goal: every button, every input, every link in the UI has a test. After the recent incident where a UI link pointed to a non-existent page, we want this category of mistake to be impossible to ship undetected.

Outline:
- New `ui/tests/e2e/` directory. Use `@playwright/test`.
- Config in `ui/playwright.config.js` — base URL `http://localhost:8080`, webServer command runs `task start` (or a fixed binary path).
- Three layers of coverage:
  1. **Interaction inventory crawler** (`e2e/_crawler/interaction-coverage.spec.js`):
     - Visits every route under the app shell.
     - For each page, enumerates every `<a>`, `<button>`, `<input>`, `<select>`, `<textarea>`. Asserts each one is visible, enabled where expected, and (for `<a>` / nav buttons) resolves to a real route — no 404, no blank page, no console error.
     - Maintains a checked-in fixture `e2e/_crawler/expected-interactions.json` listing every selector covered. The test fails if the live DOM has elements not present in the fixture (catches new orphan elements) or if the fixture lists elements no longer present.
     - This is the test that catches "link with no page assigned to it". Any new button/link added later either has to be added to the fixture (and therefore to a behavioural spec) or the test fails.
  2. **Page smoke specs** — one per page covering the canonical happy path:

### A7. Project requirements + features

Defaults I'm using — flip any that aren't what you want:
- Two separate tables (one for requirements, one for features) rather than one polymorphic table with a `kind` column. Keeps the schema honest with the user-facing concept.

#### A7.1 [x] Data model — requirements, features, task links
Outline:
- `project_requirements(id, project_id, title, body, status, position, created_at, updated_at)` — what the project must do.
  - `status` ∈ {`proposed`, `accepted`, `implemented`, `obsolete`}; default `proposed`.
- `project_features(id, project_id, title, body, status, position, created_at, updated_at)` — what the project ships.
  - `status` ∈ {`planned`, `in_progress`, `done`, `dropped`}; default `planned`.
- Status is user/agent-set only in v1 — it does NOT auto-advance based on linked task status. (If you want auto-advancement — e.g. "mark feature `done` when all linked tasks are `COMPLETED`" — say so and I'll add it as a small workflow rule.)
- `body` is markdown (existing `MarkdownEditor`).
- `task_project_links(id, task_id, kind, target_id, created_at)` where `kind` ∈ {`requirement`, `feature`}. Unique on `(task_id, kind, target_id)`. `target_id` references the respective table; integrity enforced in application code (SQLite can't FK conditionally on `kind`) plus a check at link-time that the target's `project_id` matches the task's `project_id`.
- API:
  - `GET/POST/PATCH/DELETE /api/projects/{id}/requirements`
  - `GET/POST/PATCH/DELETE /api/projects/{id}/features`
  - `GET/POST/DELETE /api/tasks/{id}/links` — POST body `{kind, target_id}`; GET returns both kinds in one response.
- Reorder by PATCHing an item with a new `position`.

### B2. [x] chat: long messages not streamed (transferred all at once)
Outline:
- Goal: the assistant reply appears progressively in the Chat page as the LLM writes it, the same UX every other LLM chat has. The user must be able to start reading before generation completes.
- Tied to A3. For Ollama and OpenAI, set `Stream: true` and pump chunks to the WS as `{type:"chat_chunk", content:"…"}`; terminate with `{type:"chat_done", usage:{…}}` carrying the A3 usage fields. Other providers fall back to whole-message replies (still wrapped in `chat_done`, but with the full content delivered in one go).
- UI: `Chat.svelte` `onMessage` creates a placeholder assistant message on the first `chat_chunk` and concatenates subsequent chunks into it; `chat_done` finalises the message, attaches the usage badge, and triggers DB save. Markdown rendering runs on every chunk append (cheap; same `marked` call as today).

- `agent-orchestrator/llm/ollama.go` (chunk streaming over NDJSON)
