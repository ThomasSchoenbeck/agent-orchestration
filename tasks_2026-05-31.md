## Bug 3 — Unify agent git transport: server is always the remote

**Status:** `[x]` done

### Problem
Two separate code paths exist for colocated vs remote agents. For colocated agents the server creates a git worktree on its own filesystem and the agent reads/writes files directly via that path. For remote agents the server returns a `RepoURL + Branch` for the agent to clone. The colocated path is where the "repository not found" push error originates (see root cause below), but more fundamentally the two-path design is the wrong model.

The immediate push error:
```
CommitAndPush failed: repo.CommitAndPush push: repository not found: repository not found
```

### Root cause of the push error (confirmed)
1. `claim.go` `provisionColocatedWorktree` falls back to `project.ID` as the slug when `project.Slug` is empty.
2. The git HTTP resolver in `git_handler.go` calls `db.GetProjectBySlug(slug)` (`WHERE slug = ?`).
3. A project ID is not a slug — the query finds nothing → 404 → "repository not found".

A second cause: if the bare repo was never initialized for the project (the project creation handler does not always call `git.InitBare`), the resolver's `gogit.PlainOpen` fails with the same error even when the slug is correct.

### Desired architecture
The server's embedded git HTTP server is the **single canonical remote** for all agents. Every agent — whether running on the same machine as the server or on a different one — always clones from and pushes to `http://{server_host}:{port}/git/{slug}.git`. There is no colocated shortcut via the local filesystem.

`Project.RemoteURL` is an optional **upstream backup/mirror** only. It allows seeding a new project from an existing git remote, or pushing completed branches to an external server for backup. Agents are never aware of it and never interact with it directly.

This unification:
- Eliminates a whole category of environment-specific bugs (the current "repository not found" error being one).
- Removes the need for the server to manage git worktrees — the server only manages bare repos.
- Makes the agent's clone/work/push cycle identical regardless of deployment topology.
- Eliminates the `mode` distinction in the claim flow (colocated vs remote becomes irrelevant for workspace provisioning).

### What to build

**Part A — Server always provides `RepoURL + Branch`** `[x]` done

Remove `provisionColocatedWorktree` from `server/claim.go`. Merge both code paths into a single `provisionWorkspace` that always returns `RepoURL` and `Branch` to the agent — never a filesystem path. The URL is always `http://{cfg.Server.ExternalHost}:{cfg.Server.Port}/git/{slug}.git` where `ExternalHost` is a new config field that defaults to `Host` (allows operators to set the externally-reachable address when the server binds `0.0.0.0`).

The `ClaimTaskResponse.WorktreePath` field is removed. `task.WorktreePath` on the server is no longer set by the server — the agent sets it on its own machine.

**Part B — Agent clones on claim, pushes on completion** `[x]` done

In `agent/agent.go` `pollLoop`, after receiving a claimed task with `RepoURL + Branch`:
1. Clone `RepoURL` to `a.LocalWorkspacePath(task.ID)` using go-git.
2. Check out `Branch` (create it if it doesn't exist, branching from `main`).
3. Set `task.WorktreePath = a.LocalWorkspacePath(task.ID)` so the executor's file tools work unchanged.
4. After the executor finishes, `CommitAndPush` back to `RepoURL` — this already works and is already in `agent/repo.go`.

The `mode` field on `Agent` and `Agent.Mode` in the DB is no longer used for workspace provisioning. It can be retained as a display label for operators who want to see where an agent is running, but it has no behavioral effect.

**Part C — Bare repo always initialized at project creation** `[x]` done (implemented as part of Bug 1+2 fix)

In `server/handlers.go` project creation handler, after inserting the project record:
1. Auto-generate `slug` from the project name if not provided (lowercase, spaces → hyphens, non-alphanumeric stripped; append short ID suffix on collision).
2. Call `git.InitBare(storage.RepoPath(p.ID))`.
3. Call `git.InitialCommit(repoPath, "main")`.
Both functions are already idempotent.

Additionally, add `GET /api/projects/{id}/init` as an admin endpoint to trigger bare repo initialization for existing projects that were created without it.

**Part D — `RemoteURL` as backup/seed** `[x]` done (pre-existing behavior: InitialPull + FetchRemote already implemented)

- On project creation, if `InitialPull == true` and `RemoteURL` is set: fetch from `RemoteURL`, reset `main` to the fetched content, then serve from the embedded server as normal.
- After each successful branch push from an agent, if the project has a `RemoteURL`, optionally mirror the branch there (configurable per project via a `mirror_pushes` flag).
- Agents never receive or use `RemoteURL`.

**Part E — Config: `ExternalHost`** `[x]` done

Add `ExternalHost string` to `ServerConfig` in `config/config.go`. When empty, falls back to `Host`. The `provisionWorkspace` function and all URL-building code uses `ExternalHost` so agents on other machines get a reachable URL.

```yaml

  port: 8080
  host: 0.0.0.0
  external_host: 192.168.1.100   # or a domain name
```

## Feature 1 — Per-provider model pricing and cost tracking

**Status:** `[x]` done

### Goal
Allow each provider to declare the models it supports along with their token prices (input and output USD per 1M tokens). Use that pricing to calculate a cost per LLM call, per task, and per chat session. Display costs in the UI.

### Current state (confirmed by code reading)
Most of the infrastructure already exists:
- `logging/cost.go` has `CostForCall(cfg, model, inputTokens, outputTokens)` using a global `cfg.Pricing` flat map.
- `config.go` has `Pricing map[string]ModelPricing` (model name → rates) and `ModelPricing{InputPerMillion, OutputPerMillion}`.
- `db/models.go` `Metric` struct already has `InputTokens`, `OutputTokens`, `Cost` fields.
- `db/models.go` `Message` struct already has `InputTokens`, `OutputTokens`.
- `db/models.go` `Provider` has only a single `ModelName string` — no per-model pricing.

### What to build

**Part A — Per-provider model list with roles and pricing (DB + config)**

Add a `Models []ProviderModel` field to the `Provider` DB struct, stored as a JSON column `models`. `ProviderModel` holds:
```go
type ProviderModel struct {
    Name             string   `json:"name"`
    Roles            []string `json:"roles"`              // roles this model serves (e.g. ["worker", "reviewer"])
    InputPerMillion  float64  `json:"input_per_million"`
    OutputPerMillion float64  `json:"output_per_million"`
}
```

Migration: `ALTER TABLE providers ADD COLUMN models TEXT NOT NULL DEFAULT '[]'`.

Update `db/providers.go` `CreateProvider`, `UpdateProvider`, and scan helpers to marshal/unmarshal the new column.

Also add `Models []ProviderModelConfig` to `config.go` `ProviderConfig` so this can be seeded from `config.yaml`:
```yaml
providers:
  - name: ollama-local
    type: ollama
    base_url: http://localhost:11434
    models:
      - name: gemma3:4b
        roles: [worker]
        input_per_million: 0.05
        output_per_million: 0.10
      - name: qwen2.5:14b
        roles: [reviewer, orchestrator]
        input_per_million: 0.20
        output_per_million: 0.40
```

When a provider declares model-level roles, those take precedence over the provider-level `Roles` list for model selection purposes. Provider-level `Roles` continues to mean "this provider can serve these roles" and is used as a fallback when no model-level role match is found.

**Part B — Role-aware model selection in the registry and router**

Currently `llm/registry.go` `roleIndex` maps `role → providerName` and `GetForRole` returns the provider's single `defaultModel`. This is too coarse when a provider has multiple models serving different roles.

Change the registry's role index to map `role → roleEntry{providerName, modelName}`:
```go
type roleEntry struct {
    providerName string
    modelName    string
}
// replace: roleIndex map[string]string
// with:    roleIndex map[string]roleEntry
```

Add `SetModelRoles(providerName string, models []db.ProviderModel)` to `Registry`. For each model that has a non-empty `Roles` list, register `role → {providerName, model.Name}` in the index. This replaces the model-name slot in the entry with the specific model, overriding the provider default.

Update `GetForRole(role)` to return the model name from the `roleEntry` directly.

Update `SetRoles(providerName, defaultModel, roles []string)` to register provider-level role entries only when no model-level entry for that role already exists (model-level wins).

In `router.go` `routeFromCache`: when `def.ModelOverride` is empty, instead of falling back blindly to `cr.defaultModel` (the provider's single model), first check whether the provider's model list contains a model whose `Roles` includes the current role. If found, use that model name. Fall back to `cr.defaultModel` only if no role-matched model exists.

Resolution order for a given role becomes:
1. DB `RoleDefinition.ModelOverride` (explicit override, highest priority)
2. Provider model list — first model whose `Roles` contains the requested role
3. Provider's top-level `ModelName` (the existing single-model default)
4. Config `cfg.Roles[role]` → `cfg.Models[modelName]`
5. Registry `GetForRole(role)` — provider-level role preference

**Part C — Cost lookup**

Update `logging/cost.go` `CostForCall` (or add an overload) to accept the provider's model list as the primary source and fall back to `cfg.Pricing` only when the provider has no pricing for that model:


## Bug 7 — Agent clone fails with HTTP 500 from embedded git server

**Status:** `[x]` done

### Error
```
clone failed, task cannot proceed: CloneOrOpen clone
"http://localhost:8080/git/<project-id>.git" → ".agent-work/worker-1/<task-id>":
unexpected client error: unexpected requesting ".../git-upload-pack" status code: 500
```

### Root cause (two compounding issues)

**Issue A — `serveUploadPack` missing session initialisation**

go-git's server library for stateless HTTP requires `AdvertisedReferences` to be called on a session before `UploadPack`. Each HTTP request creates a fresh `UploadPackSession`. `serveUploadPackInfoRefs` correctly calls `sess.AdvertisedReferencesContext`, but `serveUploadPack` creates its own new session and calls `UploadPack` directly without this step. The uninitialised session returns an error, which `httpGitError` turns into a 500.

**Issue B — `CloneOrOpen` doesn't handle `ErrEmptyRemoteRepository`**

`git.InitialCommit` creates objects via go-git's low-level storer API rather than a regular commit workflow. Even when it succeeds, go-git's server may return `transport.ErrEmptyRemoteRepository` during clone rather than serving the pack — which is the same reason all integration tests call `seedMainBranch` before cloning and `cloneRepo` in `factories_test.go` explicitly handles `ErrEmptyRemoteRepository` with a `PlainInit + CreateRemote` fallback. `CloneOrOpen` has no such fallback and treats any clone error as fatal.

### Why tests didn't catch this
- All integration tests that clone call `seedMainBranch` first (they rely on a real pushed commit, not `git.InitialCommit`).
- `cloneRepo` in `integration/factories_test.go` silently handles `ErrEmptyRemoteRepository` — the tests pass because they don't break on it.
- `TestAgentCloneOnClaim` mocks the HTTP server and never exercises the real git protocol.
- No test does the full chain: **create project → claim task → `CloneOrOpen` via embedded HTTP server**.

### Fix

**`git/httpserver.go` — initialise session before `UploadPack`**

In `serveUploadPack`, call `sess.AdvertisedReferencesContext` before `sess.UploadPack` to set up the session state. Discard the result — its only purpose here is initialisation:

```go
// Required for stateless HTTP: initialise session state before UploadPack.
if _, err := sess.AdvertisedReferencesContext(r.Context()); err != nil {
    httpGitError(w, err)
    return
}
```

Apply the equivalent fix to `serveReceivePack` for consistency.

**`agent/repo.go` — handle `ErrEmptyRemoteRepository` in `CloneOrOpen`**

When the server returns `transport.ErrEmptyRemoteRepository` (fresh bare repo with no pushed commits yet), fall back to `PlainInit + CreateRemote`, matching what `cloneRepo` in the integration tests already does:

```go
if err == transport.ErrEmptyRemoteRepository {
    repo, err = gogit.PlainInit(localPath, false)
    if err != nil { ... }
    _, err = repo.CreateRemote(&gogitconfig.RemoteConfig{
        Name: "origin",
        URLs: []string{repoURL},
    })
    ...
}
```

Also log the actual go-git error from `serveUploadPack` / `serveReceivePack` server-side before turning it into a 500, so future failures are diagnosable.

### Files to touch
- `git/httpserver.go` — add `AdvertisedReferencesContext` call in `serveUploadPack`; add error logging in `httpGitError`; same fix in `serveReceivePack`
- `agent/repo.go` — handle `ErrEmptyRemoteRepository` fallback in `CloneOrOpen`

## Feature 3 — Capability-driven role system; remove task type; fully configurable roles

**Status:** `[ ]` pending

### Problem and design intent

The system currently has two overlapping concepts that both try to describe "what kind of work is this":

- `Task.Type` (`implement`, `code review`, `write tests`, …) — restates the description; adds no routing value.
- `Task.Role` + hardcoded role list in `meta.go` — the actual routing key, but backed by a static list that cannot be changed without a code deploy.
- `RoleDefinition.TaskTypes` — an intermediary mapping that is now redundant.
- State routing (`AWAITING_REVIEW` only claimable by `reviewer`) is hardcoded in `GetNextTask` by role name. Adding a new review-capable role requires a code change.

The deeper problem: **the system does not know what it will look like in its ultimate state.** The role taxonomy will evolve. New agent roles will be introduced. Some roles will be merged or split. This must be configurable at runtime, not at compile time.

### Desired architecture

**`RoleDefinition` in the DB is the single source of truth for roles.** A role's capabilities — including which task states it can claim — are declared as a set of capability flags on the role definition itself. No role name is hardcoded in the server or agent logic; everything reads from the DB.

Task creation uses `role` as the routing key and optionally `review_role` (the name of the role that should handle the review step). Both are free-form strings that must match a `RoleDefinition.Name` in the DB. The task creation form populates the dropdowns from a live query.

### Capability flags on `RoleDefinition`

Add `Capabilities []string` (`json:"capabilities"`) to `RoleDefinition`, stored as a JSON array. Defined capability tokens:

| Capability | Meaning |
|---|---|
| `handles_review` | Role can claim `AWAITING_REVIEW` tasks whose `review_role` matches this role's name |
| `creates_tasks` | Role is allowed to create new tasks via the API (planner/orchestrator/designer pattern) |
| `handles_merge` | Role can claim `AWAITING_MERGE` tasks and execute the merge + branch cleanup |
| `handles_deploy` | Role can claim deployment-type tasks (reserved for agents with deployment credentials) |

Capabilities are strings, not an enum — operators can define their own tokens for future use. The server only acts on the four tokens above; unknown tokens are stored and surfaced in the UI but have no built-in effect.

The long-term goal is **full agent autonomy**: humans create projects and optionally seed the initial task backlog; all subsequent work — implementation, review, merge, deployment, self-improvement — is driven by agents. Every state transition must therefore be claimable by an appropriately configured agent, with human override always possible via the UI.

### Routing rules (replacing hardcoded role-name checks)

`GetNextTask` routing becomes:

| Task status | Claim condition |
|---|---|
| `BACKLOG` | `task.role IN (agent.roles)` |
| `AWAITING_REVISION` | `task.role IN (agent.roles)` |
| `AWAITING_REVIEW` | Agent's role name = `task.review_role` AND that role has `handles_review` capability |
| `AWAITING_MERGE` | Any agent whose role has `handles_merge` capability (or human via UI) |

`task.review_role` defaults to the name of the first enabled `RoleDefinition` with `handles_review`, resolved at task creation time. `AWAITING_MERGE` is claimable by any role with `handles_merge` — no per-task field needed, since the merge operation is the same regardless of which task created the PR. Humans retain the ability to approve or reject via the UI at any state; agent auto-claim is an additional path, not a replacement.

### Default role set (seeded on first run)

These replace the current hardcoded list in `meta.go` and the existing seed roles. They are inserted by `SeedRoleDefinitions` at startup only if no roles exist yet.

| Name | Label | Capabilities | Suggested tools | Notes |
|---|---|---|---|---|
| `worker` | Worker | — | read, write, diff, tests, comment | General implementation: code, tests, docs, debug, refactor |
| `reviewer` | Reviewer | `handles_review` | read, list, comment | Reviews work; makes suggestions only, no file writes |
| `planner` | Planner | `creates_tasks` | create_task, list_tasks, read, comment, web_search | Planning, architecture, orchestration, self-improvement analysis |
| `researcher` | Researcher | `creates_tasks` | web_search, read, comment, create_task | Web research, technology exploration, improvement proposals |
| `security` | Security | — | read, list, run_command, web_search, comment | Autonomous security analysis; claims `role: security` tasks from BACKLOG |
| `deployer` | Deployer | `handles_deploy`, `handles_merge` | read, run_command, comment | CI/CD, infrastructure, releases, merges — sole role with deployment credentials |
| `designer` | Designer | `creates_tasks` | read, write, comment, create_task | UI/UX design; can create implementation tasks for workers |

**Why security has no `handles_review`.** Security is not a passive participant waiting for code review tasks to enter a queue. It is an autonomous force: a planner (or a human) creates tasks with `role: security`, and security agents claim those from `BACKLOG` like any other role. A security agent scans the whole project, runs penetration tests, checks requirements compliance — it is not scoped to a single task's output. Think chaos monkey: self-directed, broad, and not triggered by individual task completions. If a reviewer discovers a security concern during a normal review, they create a new `role: security` task rather than handing off the existing one.

`planner` merges what was `orchestrator` + `architect` + `analyst`. The system prompt defines the focus; the capability `creates_tasks` gives it API access.

`researcher` is separate from `planner` because web-search-heavy workloads benefit from a different tool set and context budget. Planners create researcher tasks when they need information they don't have.

`designer` gets `creates_tasks` because after producing a design it will typically create implementation tasks for workers — e.g., "implement this component", "apply this design token change". It does not merge or deploy.

`deployer` gets both `handles_merge` and `handles_deploy`. In the autonomous model, once a PR is approved (by reviewer or security), the deployer claims it from `AWAITING_MERGE`, validates prerequisites, merges the branch, deletes it, and optionally triggers a deployment pipeline. This closes the automation loop without human intervention.

The self-improving pattern: a `planner` claims a specially-created task, reads project state (open issues, recent task outcomes, test results), and posts new tasks for `worker`, `researcher`, `security`, or `designer` as appropriate. No special machinery needed — `creates_tasks` capability + the right system prompt.

### What to build

**Part A — Remove `Task.Type` and `RoleDefinition.TaskTypes`**

`Task.Type` is set to a blank default in the migration rather than dropped (backward compatibility). Remove it from `CreateTask` insert, `CreateTaskRequest`, the type validation in `handlers.go`, the `type` select in `Tasks.svelte`, `form.type` state, and the `submit()` payload. Remove `GET /api/meta/task-types` and `handleMetaTaskTypes`. Remove `getTaskTypes` from `api.js`.

`RoleDefinition.TaskTypes []string` is similarly kept as a dead column (nullable, ignored) rather than dropped. Remove it from all CRUD writes and scans in `db/roles.go`. Remove it from the role definition form in `Roles.svelte`.

**Part B — Add `Capabilities` to `RoleDefinition`**

Add `Capabilities []string` (`json:"capabilities"`) to `RoleDefinition` in `db/models.go`. Migration: `ALTER TABLE agent_role_definitions ADD COLUMN capabilities TEXT NOT NULL DEFAULT '[]'`. Update `CreateRoleDefinition`, `UpdateRoleDefinition`, and both scan functions in `db/roles.go` to marshal/unmarshal the new column. Add the field to the role form in `Roles.svelte` — a multi-select or tag input with the known tokens listed as suggestions (free text also allowed).

**Part C — Add `ReviewRole` to `Task`; make AWAITING_REVIEW routing capability-driven**

Add `ReviewRole string` (`json:"review_role,omitempty"`) to `db.Task`. Migration: `ALTER TABLE tasks ADD COLUMN review_role TEXT NOT NULL DEFAULT ''`. On task creation, if `review_role` is not supplied, resolve it to the name of the first enabled `RoleDefinition` with `handles_review` in its capabilities, or fall back to the string `"reviewer"` if none is found.

Update `GetNextTask` (from Bug 9 Part A) to replace hardcoded role-name checks with capability joins:

```sql
(
  -- Normal work: task role matches agent role
  (status IN ('BACKLOG', 'AWAITING_REVISION') AND role IN (<agent_roles>))

  OR

  -- Review: agent's role name matches task.review_role AND that role has handles_review

    status = 'AWAITING_REVIEW'

```

**Part G — Seed default roles**

Replace the existing hardcoded seed roles (in `main.go` or wherever they currently live) with the new seven-role set defined above. `SeedRoleDefinitions` only inserts roles that do not already exist by name, so existing user-created roles are untouched.

**Part H — Document patterns in `AGENTS.md`**

Document four patterns enabled by capabilities:
1. **Worker pattern** — claims `BACKLOG` tasks, implements, pushes, enters `AWAITING_REVIEW`.
2. **Review pattern** — any role with `handles_review` can be set as `review_role` on a task; role's system prompt and tools define the review style. Reviewer approves → `AWAITING_MERGE`.
3. **Merge pattern** — any role with `handles_merge` claims `AWAITING_MERGE`, validates, merges branch into main, deletes branch, completes task. Deployer role does this by default; can also trigger a deployment pipeline post-merge.
4. **Planner/self-improvement pattern** — claims tasks with role `planner` or `researcher`; uses `creates_tasks` capability to post new tasks. Planners can also be triggered to survey the project and propose improvements, creating tasks for any role as needed.
5. **Security chaos-monkey pattern** — security agent claims `BACKLOG` tasks with `role: security`; it is not scoped to individual task reviews but operates on the whole project. Planners or humans create security tasks explicitly; the security agent runs broad analysis, pen tests, and requirement checks independently.
