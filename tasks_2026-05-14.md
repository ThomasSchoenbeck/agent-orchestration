## Architecture notes

### Three dedicated log tables

Rather than extending the existing `logs` table, the design uses three dedicated tables:

- **`agent_logs`** — agent lifecycle events (structured, high-volume, short-lived)
- **`task_logs`** — task lifecycle events (structured, medium-volume, longer-lived)
- **`logs`** — system/API/MCP logs (existing table, info/warn/error, low-volume)

This keeps retention logic clean per category and avoids a bloated general-purpose table.

### Hardcoded log event types

Log types are defined in code — they are not user-configurable. Users can only control retention per type.

**Agent event types** (emitted by the agent poll loop and executor):

> `agent_poll_start` and `agent_poll_no_task` were removed — too high volume, too low value. Polling visibility is covered by the `/api/agents/:id/poll-status` endpoint instead.

| Event type | Description | Default retention |
|---|---|---|
| `agent_registered` | Agent joined or re-registered | 90 days |
| `agent_poll_task_found` | Poll found a matching task (roles searched, task ID) | 7 days |
| `agent_claim_attempt` | Agent tried to claim a task | 3 days |
| `agent_claim_success` | Claim succeeded | 14 days |
| `agent_claim_failed` | Claim failed (already taken, wrong status) | 7 days |
| `agent_execute_start` | Task execution began | 14 days |
| `agent_llm_call` | An LLM round was made — includes `execution_id`, model, token count, latency, round number | 7 days |
| `agent_tool_call` | A tool was invoked — includes `execution_id`, tool name, input/output summary | 7 days |
| `agent_tool_error` | Tool exists but returned an error (distinct from LLM failure) | 30 days |
| `agent_context_overflow` | Hit the LLM token limit; memory was truncated | 14 days |
| `agent_reasoning_step` | Chain-of-thought / inner monologue captured per LLM round | 7 days |
| `agent_retry_backoff` | Task failed; retry scheduled — includes attempt number and backoff duration | 7 days |
| `agent_human_approval_req` | Agent paused awaiting human-in-the-loop intervention | 90 days |
| `agent_execute_complete` | Task finished successfully | 30 days |
| `agent_execute_failed` | Task execution failed (error attached) | 30 days |
| `agent_offline` | Agent stopped sending heartbeats | 90 days |

**Trace / execution ID:** The executor generates a single `execution_id` UUID at the start of each task run. Every `agent_llm_call`, `agent_tool_call`, `agent_tool_error`, `agent_context_overflow`, and `agent_reasoning_step` event for that run shares the same `execution_id`. This allows the Svelte UI to reconstruct the complete LLM+tool timeline for a single execution and filter/group by it.

**Task event types** (emitted by DB layer or server handlers):

| Event type | Description | Suggested default retention |
|---|---|---|
| `task_created` | Task was inserted | 90 days |
| `task_updated` | Metadata or priority changed | 14 days |
| `task_queued` | Status moved to queued/planned | 30 days |
| `task_claimed` | Agent claimed the task | 30 days |
| `task_started` | Execution began (started_at set) | 30 days |
| `task_llm_round` | Each LLM iteration (round #, tokens) | 3 days |
| `task_tool_call` | A tool call within execution | 3 days |
| `task_result_submitted` | Result payload submitted | 60 days |
| `task_completed` | Task completed successfully | 90 days |
| `task_failed` | Task failed (error in result) | 90 days |
| `task_timed_out` | Task timed out and was reset | 30 days |
| `task_requeued` | Task manually or automatically requeued | 30 days |

### Testing policy — temporary databases

**All DB tests must use temporary, isolated databases that are discarded after the test.** No test may write to `data/orchestrator.db` or `data/logs.db`.

The existing pattern for the main DB is already correct and must be followed for the new log DB as well:

```go
// db/testhelpers_test.go  (shared across all db package tests)

// openTestDB opens a fresh main DB in a temp directory, runs migrations,
// and registers a cleanup to close and delete it when the test ends.
func openTestDB(t *testing.T) *db.Database {
    t.Helper()
    d, err := db.Open(filepath.Join(t.TempDir(), "test.db"))
    if err != nil {
        t.Fatalf("openTestDB: %v", err)
    }
    t.Cleanup(func() { _ = d.Close() })
    return d
}

// openTestLogDB opens a fresh log DB in a temp directory, enables WAL,
// and registers cleanup. Used for agent_logs and task_logs partition tests.
func openTestLogDB(t *testing.T) *db.LogDatabase {
    t.Helper()
    ld, err := db.OpenLogDB(filepath.Join(t.TempDir(), "test_logs.db"))
    if err != nil {
        t.Fatalf("openTestLogDB: %v", err)
    }
    t.Cleanup(func() { _ = ld.Close() })
    return ld
}

// openTestDBPair opens both a main DB and a log DB, both temporary.
func openTestDBPair(t *testing.T) (*db.Database, *db.LogDatabase) {
    t.Helper()
    dir := t.TempDir()
    d, err := db.Open(filepath.Join(dir, "test.db"))
    if err != nil { t.Fatalf("openTestDBPair main: %v", err) }
    ld, err := db.OpenLogDB(filepath.Join(dir, "test_logs.db"))
    if err != nil { t.Fatalf("openTestDBPair log: %v", err) }
    t.Cleanup(func() { _ = d.Close(); _ = ld.Close() })
    return d, ld
}
```

Rules:
- Use `t.TempDir()` — Go creates the directory and removes it (and everything in it) when the test ends, including on failure.
- Never hardcode a path. Never use `os.TempFile` with a fixed name that could collide across parallel tests.
- Tests that need both databases use `openTestDBPair`.
- Integration tests that spin up a full `Server` must pass temp-DB instances into the server constructor rather than letting the server open its own files.

### SQLite architecture

**WAL mode** is enabled on both the main DB and the log DB at connection open time (`PRAGMA journal_mode=WAL`). WAL allows concurrent readers and one writer without `SQLITE_BUSY`, which is critical when the agent executor, poll loop, and HTTP handlers all write logs simultaneously.

**Separate log DB** (`data/logs.db`) holds `agent_logs` and `task_logs` partitions, isolated from the main `data/orchestrator.db`. High-frequency log writes cannot block main DB operations (task claims, heartbeats, API responses).

**Daily partition tables** replace a single monolithic log table. Each day gets its own table:

```
agent_logs_2026_05_14   ← written to on 2026-05-14
agent_logs_2026_05_15   ← written to on 2026-05-15
task_logs_2026_05_14
...
```

Dropping an old day is an instant metadata operation (`DROP TABLE`), not a heavy `DELETE` that fragments the file. Tables are created lazily on first write; a mutex-guarded in-process set avoids redundant `CREATE TABLE IF NOT EXISTS` calls. Queries `UNION ALL` across the partition tables that overlap the requested time window.

**Why not per-type partitions:** `type × day` would produce ~16 agent types × 365 days ≈ 5 840 tables/year — manageable for SQLite but query generation and schema migrations multiply. Daily-only partitioning yields 365 × 2 = 730 tables/year maximum; in practice far fewer since old ones are dropped continuously.

**Mixed-retention cleanup (two-pass):**
1. `DROP TABLE` any partition older than the *maximum* retention for the category (e.g., 90 days). This handles the bulk of data instantly.
2. For types whose retention is shorter than the oldest kept partition, run a fast targeted `DELETE WHERE event_type IN (...) AND timestamp < cutoff` on the small live dataset (only recent partitions, e.g., ≤ 7 days of rows).

**Precision note:** A row for a 3-day-retention type may live up to 24 h longer than configured (the remainder of its partition day). Acceptable for log data; documented in the Settings UI tooltip for those types.

### Retention config model

Settings are stored in a `platform_settings` table (key/value). Keys follow the pattern:

- `log.retention.agent.default_days` — default for all agent event types
- `log.retention.task.default_days` — default for all task event types
- `log.retention.system.default_days` — default for the general `logs` table
- `log.retention.agent.<event_type>_days` — per-type override (takes precedence over default)
- `log.retention.task.<event_type>_days` — per-type override

Effective retention for a type = type-specific override if set, else category default.

Config file seeds these values on first startup; DB wins thereafter (UI changes persist).

#### [ ] #19 — Implement daily-partition log tables with DROP-based retention

**Status:** pending  
**Blocked by:** #18  
**Tested by:** #21

See the SQLite architecture section above for the full rationale.

Key implementation points:

- **Partition naming:** `agent_logs_2026_05_14`, `task_logs_2026_05_14` — one table per calendar day in UTC.
- **Lazy creation:** tables are created on first write for that day (`CREATE TABLE IF NOT EXISTS`). A mutex-guarded in-process set tracks which tables already exist to avoid round-trips.
- **Query generation:** `ListAgentLogs` / `ListTaskLogs` compute the set of partition table names that overlap `[since, until]`, check each exists (query `sqlite_master`), and build a `UNION ALL` query. Helper: `func partitionTablesForRange(prefix string, since, until time.Time) []string`.
- **Retention cleanup (two-pass, replaces task #15's DELETE-only approach):**
  1. `DROP TABLE` any partition older than the *maximum* retention across all types for that category.
  2. For types with shorter retention than the oldest live partition, run a targeted `DELETE WHERE event_type IN (...) AND timestamp < cutoff` on the live partitions only.
- **Precision caveat:** data for short-retention types may persist up to 24 h beyond their configured window (remainder of the partition day). Document this in the Settings UI.
