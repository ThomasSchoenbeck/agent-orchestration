## Why

Branches are currently hardcoded as `task/<id>` (a UUID), which is unreadable. The user wants
agents to create branch names derived from the task name, prefixed by a **task type**: normal →
`feature`, bug → `bug`, hotfix → `hotfix`, release → `release`, with room for more. Task types
must be definable in a **config section** (for initial seeding, like the other config parts) and
editable in a **Settings page section** afterwards.

## Decisions (confirmed with user 2026-06-10)

- **Full rework** of branch naming. Branch = `<prefix>/<human-readable-name>` driven by a
  **per-type template**. Branches no longer embed the task ID.
- **Push resolution by lookup, not parsing.** Since the branch no longer contains the id, the
  generated branch is **persisted on the task row** (`tasks.branch`) and the git post-receive hook
  resolves the task via a DB lookup. Agents continue to work with the task **id** (delivered in the
  claim response); only the git branch label changes.
- **Type scope = branch prefix only.** Task type does not affect routing, review, or priority. It
  is naming metadata. (Does not re-add the behavior dropped in Feature 3.)
- **Config seed + Settings DB (source of truth) + Settings UI.** A `task_types:` config section
  seeds the DB on first run only; the Settings page is authoritative afterwards (mirrors the
  existing `role_definitions` / `orchestrator` seeding contract).
- **IDs as references.** `tasks.task_type_id` references `task_types.id`. (User: primary keys stay
  ids; for now only the *branch* becomes name-derived.)
- **Old data is disposable.** App currently holds only dummy data, so the migration is purely
  additive and existing task rows may be truncated rather than backfilled.

## Data model

`task_types` table:

| column          | type    | notes                                                        |
| --------------- | ------- | ------------------------------------------------------------ |
| `id`            | TEXT PK | generated id (referenced by `tasks.task_type_id`)            |
| `key`           | TEXT    | unique slug: `normal`, `bug`, `hotfix`, `release`            |
| `label`         | TEXT    | display name: `Normal`, `Bug`, `Hotfix`, `Release`           |
| `branch_template` | TEXT  | e.g. `feature/{slug}`, `bug/{slug}`                          |
| `is_default`    | INTEGER | exactly one row true (used when a task has no explicit type) |
| `sort_order`    | INTEGER | UI ordering                                                  |
| `created_at`    | …       |                                                              |
| `updated_at`    | …       |                                                              |

`tasks` additions: `task_type_id TEXT` (FK → `task_types.id`, defaults to the default type) and
`branch TEXT` (persisted generated branch; unique per project).

**Default seeds** (also the config defaults):

| key     | label   | branch_template     |
| ------- | ------- | ------------------- |
| normal  | Normal  | `feature/{slug}`    |
| bug     | Bug     | `bug/{slug}`        |
| hotfix  | Hotfix  | `hotfix/{slug}`     |
| release | Release | `release/{slug}`    |

`normal` is the default (`is_default = true`).

## Branch template

Placeholders supported by the generator: `{slug}` (slugified `payload.title`), `{id}` (full task
id), `{shortid}` (first 8 chars), `{type}` (type key). Defaults use `{slug}` only.

`slugify`: lowercase; non-alphanumeric → `-`; collapse repeats; trim leading/trailing `-`; cap
length (e.g. 50 chars); empty title → falls back to `{shortid}`.

**Collision handling:** the resolved branch must be unique per project. If a template without an id
placeholder produces a name already used by a *different* task in the project, append `-{shortid}`.
This keeps names readable while guaranteeing the git-hook lookup stays 1:1.

## B1 — Worker tasks reach COMPLETED without review, branch left unmerged

**Symptom (reported):** Of several worker tasks, most are in `AWAITING_REVIEW`, but two went to
`COMPLETED` without any review, and their branches were never merged into main.

**Verified code path:** The task `result` endpoint (`server/handlers.go`, `case "result":`
~`:760-774`) takes the **client-supplied** `req.Status`, and:

```go
if req.Status == "" { req.Status = "completed" }      // empty → completed
if err := s.db.SubmitTaskResult(ctx, id, req.Result, req.Status); err != nil { ... }
```

It writes the status verbatim with **no transition guard** and **no merge step**. The normal worker
flow goes through `SubmitForReview` → `AWAITING_REVIEW` → reviewer approval → `AWAITING_MERGE` →
merge (`server/reviews.go:86-93`, `openPRForApprovedReview`) → `COMPLETED`. Anything that submits a
result with `status="completed"` (or **empty**, which defaults to completed) bypasses the entire
review/merge gate, so the branch is never merged. `SubmitTaskResult(COMPLETED)` is intended only for
planner/`creates_tasks` tasks (`agent/executor.go:168`); the seeded **worker role has no
capabilities** (`db/seed_roles.go`), so a worker task must never legitimately self-complete.

## B2 — AWAITING_REVIEW tasks not claimed by review agents (review-role match gap)

**Symptom (reported):** All `AWAITING_REVIEW` worker tasks — i.e. tasks whose implementation role is
`worker` — are never picked up by review agents.

**Verified code path:** `GetNextTaskWithSkills` (`db/tasks.go:213-260`) builds the claimable query.
The **normal-work** clause deliberately bridges id/name forms:

```go
matchRoles := d.ExpandRoleMatch(ctx, roles)   // handles id<->name during id migration
clauses = append(... "role IN (...matchRoles...)" ...)
```

…but the **review** clause does **not**:

```go
// reviewerRoles come from capabilityRoles() = role *ids* with handles_review
clauses = append(... "(status='AWAITING_REVIEW' AND review_role IN (...reviewerRoles...))" ...)
```

So if a task's `review_role` is stored in a form that doesn't match the reviewer's role **ids**
(name-form left over from the role-id migration — see `2026-06-04-role-id-migration-plan.md`), or is
empty / set to a non-review role, the `IN` test fails and **no reviewer ever matches**. This is the
same id/name asymmetry the normal clause was patched for; the review clause was missed.

**Hypotheses (confirm via the stuck tasks' actual `review_role` values):**
1. **id/name asymmetry** — `review_role` holds a role *name* while `reviewerRoles` are *ids* (or
   vice versa). The review clause lacks `ExpandRoleMatch`. **Most likely.**
2. `review_role` is empty or equals the implementation role (`worker`) — `create_work_package`
   (`tools/backend.go` `WorkPackageInput` has **no review_role**) relies on `CreateTask` →
   `defaultReviewRole` (`db/tasks.go:25-26,383`); if that returned `""` at creation time (no enabled
   `handles_review` role yet), the task is unclaimable for review.

**Fix direction (with B4):** Two parts —
1. Apply `ExpandRoleMatch` bridging to the `review_role` comparison so a set review role matches
   regardless of id/name form (mirror the normal-work clause).
2. **Remove the auto default reviewer** (`defaultReviewRole`, per user): stop assigning a specific
   reviewer at creation. An **empty** `review_role` now means **"any review-capable agent"** — the
   review clause becomes: `status='AWAITING_REVIEW' AND ( (review_role='' OR review_role IS NULL)
   OR review_role IN (reviewerRoles, expanded) )`, gated by the claiming agent having
   `handles_review`. A **set** `review_role` restricts to that role.

This makes the stuck tasks claimable (empty → any reviewer) and is the same change B4 needs.

**Success criteria / tests:**
- Failing test: an `AWAITING_REVIEW` task with a **set** `review_role` in the **name** form is
  offered to a reviewer agent whose roles are **ids** (and vice versa) via `GetNextTaskWithSkills`.
- Test: a task with **empty** `review_role` is claimable by **any** `handles_review` agent, and
  **not** claimable by a non-review agent.
- Test: a task with a **specific** `review_role` is claimable only by that review role.

**Files:** `db/tasks.go` (`GetNextTaskWithSkills` review clause; `defaultReviewRole`), possibly the
work-package creation path, tests in `db/task_role_queue_test.go` / `db/tasks_*_test.go`.

**Implemented 2026-06-10 (B2 backend):**
- `db/tasks.go` — review clause in `GetNextTaskWithSkills` now: `status='AWAITING_REVIEW' AND
  (review_role='' OR review_role IS NULL OR review_role IN (<ExpandRoleMatch(reviewerRoles)>))`. So
  empty review_role = any `handles_review` agent, and a set review_role matches id **or** name form.
- `db/tasks.go` — removed `defaultReviewRole`; `CreateTask` no longer auto-assigns a reviewer (empty
  review_role stays empty).
- Tests (`db/getnexttask_routing_test.go`): replaced `TestCreateTask_ResolvesDefaultReviewRole` /

  `TestGetNextTask_EmptyReviewRoleClaimableByAnyReviewer` and
  `TestGetNextTask_ReviewRoleNameMatchesIDReviewer` (the id/name bug). Existing capability-routing

## Resolved decisions (2026-06-10, via clarifying questions)

1. **Branch timing** — generated **at the start of work** (claim) and **immutable** afterwards (git
   constraint; no branch-moving). No regeneration on edit. (T3/T5)
2. **Delete-in-use task type** — **reject** deletion while tasks reference it. (T7)
3. **Review "auto"** — **removed**. Empty review role = **any review-capable agent**; set a specific
   role to restrict. `defaultReviewRole` creation-time assignment is dropped. (B2 + B4)
4. **Context size granularity** — **per message** to the LLM (per call), shown in the timeline so
   growth is visible — not a per-task peak. (T13)
5. **Context "used" value** — **total prompt incl. cached** = `input + cache_read + cache_creation`
   tokens (true window occupancy). (T13)
6. **Cost breakdown** — Providers box shows **total**; the cost-breakdown page shows **input and
   output separately** (separate token *and* cost columns). (T14)
7. **B3 log scope** — humanize **both** the server poll/pull log **and** the agent-side pickup
   comment / executor `role=…` lines. (B3)

## Remaining implementation sub-decisions (minor, decide during build)
