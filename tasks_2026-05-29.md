## Task 3 — Fix agent execution pipeline: logging, LLM visibility, review flow, and push

**Status:** `[x]` done

### How the colocated workflow actually works (context)
In colocated mode the **server** — not the agent — provisions the worktree. During `ClaimTask`, the server calls `CreateWorktree` which clones the project's bare repo into a local directory and checks out the task branch. It also writes `.agent_context/` context files (task description, project rules, last review). The claim response returns `worktree_path`; the agent receives this path and works inside it directly. The agent never clones anything itself. This entire setup is currently invisible to the user — nothing is logged to the task.

### Root cause summary

**Gap 1 — Routing fails silently before the LLM is ever called.**
`execute()` tries `RouteByTaskType(task.Type)` then `RouteByRole(task.Role)`. Both failures are logged at `Debug` level only — never shipped to the server. If the role in the DB has no `provider_id` set (common when the role was seeded or created without explicitly linking a provider), `routeFromCache` fails. The config-file fallback also typically fails. The provider role-preference fallback (`GetForRole`) only works if the provider's `roles` list was set at agent startup. When all three fail, `execute()` returns an error immediately — the LLM is never contacted — and the only record of this is an `Error`-level log that the user must know to look for in the logs tab. This is the confirmed reason the local LLM receives no calls.

**Gap 2 — Worktree provisioning never logged to the task.**
`provisionColocatedWorktree` logs to server stdout only. No task comment, no task log entry. User sees the directory appear on disk with no corresponding event in the UI.

**Gap 3 — Review step completely skipped.**
After a worker task's LLM run, `Run()` calls `SubmitTaskResult(TaskStatusCompleted)`. `TaskStatusAwaitingReview` is defined but never used. `client.SubmitForReview()` exists but is never called. The correct sequence after a worker finishes: commit files → push branch to the project repo → post a comment saying which branch was pushed → call `SubmitForReview` to hand off to a reviewer agent.

**Gap 4 — ZeroHash worktree has no remote; push always fails.**
When `CreateWorktree` encounters a ZeroHash base (repo had no commits at claim time), it falls back to `gogit.PlainInit` without configuring a remote. `CommitAndPush` with an empty `remoteURL` then fails because there is no "origin". This is a push to the bare repo, which IS the server's repo. Fix: after `PlainInit`, call `repo.CreateRemote("origin", repoPath)` so the push has a destination. New projects now always have an initial commit on main (from earlier fix), so this path is rarer — but the code remains broken for any project that was initialized before that fix.

**Gap 5 — `projectID` missing from task logger.**
Log entries are tagged with `task_id` and `agent_id` but not `project_id`. Project-scoped log views in the UI receive no agent log entries.

**Gap 6 — Routing not validated at agent startup.**
Agent logs "executor wired (LLM providers: N)" at startup but never checks whether each of its roles actually resolves to a provider. A misconfigured role (no `provider_id`, no config mapping, no provider role-preference) stays silent until a task is claimed and fails. Users have no way to know the agent is misconfigured until they look at a failed task's log.

### Changes required

#### `agent/executor.go`
- Promote routing attempt logs to Info: `tlog.InfoCtx(ctx, "routing task type=%q role=%q", task.Type, task.Role)` before the route calls; `tlog.InfoCtx(ctx, "route resolved provider=%q model=%q", ...)` on success; `tlog.ErrorCtx(ctx, "routing failed: %v", err)` on total failure (currently only returned as an error, not logged at the call site).
- Promote LLM call logs to Info: `tlog.InfoCtx(ctx, "calling LLM provider=%q model=%q round=%d", ...)` and `tlog.InfoCtx(ctx, "LLM response stop=%s tool_calls=%d tokens=%d", ...)`.
- After `commitTaskWork` produces a new commit SHA: post a comment "Branch `task/<id>` pushed to project repo. Commit: `<sha12>`." then call `e.client.SubmitForReview(ctx, task.ID)` instead of `SubmitTaskResult(Completed)`.
- If worktree is clean after LLM run (nothing committed): submit `TaskStatusCompleted` with result note "No file changes produced."
- Set project ID on logger at start of `Run()`: derive from `task.ProjectID`.

#### `agent/agent.go`
- In `buildAgent`, after `rtr.LoadFromDB`, call `rtr.RouteByRole(role)` for each agent role and log at Info: `"role %q resolves to provider=%q model=%q"` (success) or Warn: `"role %q has no route — tasks for this role will fail immediately"` (failure).

#### `server/claim.go` — `provisionColocatedWorktree`
- After `CreateWorktree` succeeds, create a task log entry: `"Worktree provisioned at <path> on branch task/<taskID> (base: main)"`. Level info, associated with `agentID` and `taskID`.
- Post a task comment from the server: `"Worktree ready on branch \`task/<taskID>\`. Agent is starting."` This appears before the agent's own start comment.

#### `git/worktree.go` — ZeroHash path
- After `gogit.PlainInit(worktreePath)`, open the new repo and call `CreateRemote("origin", repoPath)` so `CommitAndPush` can push back to the bare repo.

## Task 4 — Auto-inject `repo_path` into file tool calls

**Status:** `[x]` done

### Problem
The LLM calls `write_file` (and other file tools) without providing `repo_path`, even though the system prompt says to use the workspace directory as `repo_path`. The error `{"error":"missing required argument \"repo_path\""}` is returned to the LLM, which then retries and fails again, burning through all 10 tool rounds with no output.

### Root cause
`repo_path` is listed as a required parameter in the tool definition. The LLM often omits it when focused on file content. The agent always knows `task.WorktreePath` but doesn't pass it to the tool registry at the call site.

### Fix
In `executor.go`, before calling `e.tools.ExecuteJSON`, intercept file-tool calls and inject `repo_path` from `task.WorktreePath` when it is missing or empty. This makes the LLM's omission harmless.

```go
// In execute(), before ExecuteJSON:
if task.WorktreePath != "" {
    if _, ok := tc.Arguments["repo_path"]; !ok {
        tc.Arguments["repo_path"] = task.WorktreePath
    }
}
```

Additionally, make `repo_path` optional in the `write_file`, `read_file`, `list_files`, `apply_diff`, and `run_tests` tool definitions (remove it from `Required`), so the LLM is never penalised for omitting it.

### Files to touch
- `agent/executor.go` — inject `repo_path` at the call site before `ExecuteJSON`
- `tools/code.go` — remove `repo_path` from `Required` list on all file tools; document that the executor injects it

### Tests
- `TestExecutor_InjectsRepoPath` — mock a tool call for `write_file` with no `repo_path` argument; verify the executor injects `task.WorktreePath` before the tool is called
- `TestWriteFile_MissingRepoPath` — call `write_file` without `repo_path` (simulate old LLM output); verify the tool returns an error explaining the argument is missing (existing behaviour — confirms the injection must happen at executor level)
