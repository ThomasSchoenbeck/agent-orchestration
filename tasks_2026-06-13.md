# Tasks — 2026-06-13: Subagents (spawnable "subagent skills") + session checkpoint/handoff

Progress markers: `[x]` done · `[ ]` pending · `[~]` in progress

## Goal

Let a running agent (started via `agent --roles …` or spawned by the server) **delegate a
context-heavy subtask to a subagent**: a goroutine inside the same agent process that runs its own
LLM↔tool loop, does focused work (e.g. investigate a freshly-checked-out codebase), and returns a
**summary** to the main loop. The heavy context lives and dies inside the subagent, so it never
inflates the main session's token budget. Subagent kinds are configured in Settings as a new
**Subagent Skill** entity. Finally, for tasks that need a lot of main-agent work, add a **session
checkpoint**: persist the main loop's messages + a summary and continue in a compacted ("new")
session.

## Confirmed decisions (from clarification rounds)

1. **New first-class entity `SubagentSkill`** — separate from persona Skills, with its own Settings
   panel. (Persona skills describe an agent's specialization; subagent skills are *spawnable units of
   work*. Keeping them distinct avoids overloading "skill".)
2. **Invocation = a single built-in tool `run_subagent(skill, instructions)`.** It starts as a tool
   call: the agent's base/system prompt instructs the LLM *when* to emit it (e.g. "to investigate the
   checked-out codebase, call `run_subagent` with `skill="investigate_codebase"` and a summary of what
   you need to find out"). Receiving that tool call, the executor spawns the matching subagent. One
   tool to allowlist; subagent kinds are data, not code.
3. **Model = inherited from the spawning agent.** v1 reuses the main agent's resolved provider/model
   for the subagent (no role routing, no new seeded roles). _Future enhancement, not in scope: route
   the subagent by a `route_role` on the skill so a model can be prioritized per subtask._
4. **Synchronous from the LLM's view.** The `run_subagent` tool round blocks while the subagent
   goroutine runs; the subagent's summary is returned as the tool result and the main loop continues.
   The goroutine is for isolation/timeout, not concurrency the main agent observes.
5. **Gating = none beyond the tool allowlist.** `run_subagent` is added to the default tool allowlist
   of all main-agent roles (worker, reviewer, planner/orchestrator, deployer, researcher, designer,
   security). Subagent skills are enabled globally. No per-role "spawnable list" in v1.
6. **v1 subagent skill = `investigate_codebase` (read-only).** Tool allowlist = read/search tools over
   the main agent's worktree. A **coding** subagent (read/write/create) is Phase E — same engine,
   different allowlist.
7. **No nesting in v1.** A subagent's tool allowlist excludes `run_subagent`, so subagents can't spawn
   subagents.
8. **Token isolation.** Subagent token usage is recorded against the task (for cost) but is **not**
   appended to the main loop's message history — only the summary is. That is the whole point.
9. **Session checkpoint = final phase (F).** Persist the main task loop's messages + a generated
   summary, then compact in-memory messages to `[system, summary]` and continue.

## Phase C — `run_subagent` tool + executor spawn (the core)

- [ ] **C1** — **Register `run_subagent`.** A built-in tool with params `skill` (string — subagent
  skill name) and `instructions` (string — the main agent's summarized ask). Its registry handler is a
  **stub/no-op** — actual spawning is intercepted in the executor loop (C2), because the handler has no
  access to the per-task route/worktree. Register it alongside the other code tools and wire it in
  `buildAgent`.
  - Files: `tools/subagent.go` (new — `RegisterSubagentTool`), `tools/executor.go` (no change beyond
    registry use), `main.go` (call `RegisterSubagentTool`), `tools/subagent_test.go`.
  - Verify: tool appears in the registry with the right schema; included only when allowlisted.

- [ ] **C2** — **Executor interception + nested loop.** In `agent/executor.go:execute()`'s tool-call
  dispatch, special-case `run_subagent`: (1) look up the skill by name from the executor cache (must
  be enabled — else return a tool-error string the LLM can react to); (2) build the subagent system
  prompt from `skill.prompt_template` with `instructions` injected; (3) run a **nested LLM↔tool loop**
  in a goroutine with a derived `context.Context` (timeout + cancel), using the **same `RouteResult`
  provider/model** as the main task, with `toolDefs` filtered to `skill.tool_allowlist` over the
  **same worktree** as the main agent; (4) bound by `skill.max_rounds`; (5) take the subagent's final
  message as the result and return it (or a short wrapper) as the `run_subagent` tool result to the
  main loop. The nested loop **reuses** the existing tool-loop machinery — factor the loop body so it
  can run for both the main task and a subagent (avoid a second copy that drifts).
  - Implementation notes / things to confirm while building:
    - **Worktree resolution.** Confirm how the code tools (`read_file`, etc.) resolve their working
      directory (ctx value vs registry/backend state). The subagent must hit the **same** worktree;
      reuse the same `tools.Registry` filtered by allowlist rather than constructing a new backend.
    - **Summary.** v1: the subagent's `prompt_template` already instructs it to end with a concise
      findings summary, so the final assistant message *is* the summary — no extra summarization call.
      Keep it that way unless the final message is empty (then return the last tool round's digest).
    - **No nesting:** the subagent's filtered allowlist must never include `run_subagent`.
  - Files: `agent/subagent.go` (new — `runSubagent(ctx, route, skill, instructions) (summary string,
    stats, err)`), `agent/executor.go` (dispatch hook + loop-body factoring), `agent/subagent_test.go`.
  - Verify (mocked LLM): a `run_subagent` call runs a bounded nested loop, the subagent's tool calls
    are restricted to the allowlist, and the summary string is returned into the main loop's messages;
    an unknown/disabled skill returns a tool-error (loop continues, doesn't crash); `max_rounds` and
    timeout are honored.

- [ ] **C3** — **Token/cost accounting + logging, isolated from main history.** Subagent
  input/output tokens and cost are added to the task's `execStats` (so cost views stay accurate) and
  logged as task events (a distinct event/source label, e.g. `subagent`, with the skill name), but the
  subagent's intermediate messages are **not** appended to the main loop's `messages` — only the
  returned summary is. Reuse the existing `logging.CostForCallWithProvider` + task-event logging.
  - Files: `agent/subagent.go`, `agent/executor.go` (fold subagent stats into task stats), `logging/*`
    if a new event label is needed, `agent/subagent_test.go`.
  - Verify: after a subagent run, task token totals include the subagent's usage; the main `messages`
    slice grew by exactly the summary, not the subagent transcript.

- [ ] **C4** — **Base prompt + allowlist defaults.** Add a system-prompt fragment (in
  `buildSystemMessage` / the tool-docs section) telling the agent **when** to call `run_subagent`
  (e.g. "before reading large amounts of code yourself, delegate exploration: call `run_subagent` with
  `skill="investigate_codebase"` and a summary of what you need to find; you'll get back a digest").
  Add `run_subagent` to `defaultToolsForRole` for the main-agent roles and to the seeded role
  allowlists in `db/seed_roles.go` + `config.example.yaml` (fresh DBs only; existing DBs toggle it on
  the Roles page — note this in the risks section).
  - Files: `agent/executor.go` (`buildSystemMessage`/`buildToolDocs`, `defaultToolsForRole`),
    `db/seed_roles.go`, `config.example.yaml`, `agent/executor_internal_test.go`,
    `db/seed_roles_test.go`.
  - Verify: a worker/reviewer/etc. route includes `run_subagent` in its `toolDefs`; the prompt fragment
    is present.

## Suggested order

**A → B → C** is the spine: nothing works until the entity exists, the agent can fetch it, and the
executor can spawn it. **C2 is the hard, central task** (nested loop, worktree sharing, returning a
summary) — do it on a mocked LLM with the read-only seed only. Then **D** (UI) makes it operable.
**E** is nearly free once C works (data-only). **F** (session checkpoint) is the most independent and
highest-blast-radius piece (touches the main loop's message lifecycle) — do it last, behind a
threshold so it can't destabilize normal short tasks.

## Risks / honest scope notes

- **C2 is a real behavior change to the agent loop.** Factor the loop body so the main task and the
  subagent share one implementation; a second copy will drift. The biggest unknown is **worktree
  resolution** for the code tools — settle that first (read `tools/code.go` + how `read_file` finds
  its root) before writing the nested loop.
- **Inheriting the model is a deliberate v1 simplification.** Your original idea ("prioritize a model
  for that subtask via role") is dropped for now; the entity has room to add a `route_role` later
  without schema churn. Flag if you'd rather build role-routing now.
- **Existing-DB allowlists.** Adding `run_subagent` (C4) / `checkpoint_session` (F3) to seeded roles
  only affects **fresh** DBs; existing roles must toggle the tool on the Roles page (or add a small
  backfill migration — say the word and I'll add it).
- **Token isolation must be tested explicitly** (C3) — it's the entire justification for the feature;
  a regression that appends the subagent transcript to the main history silently defeats it.
- **Coding subagent + concurrency.** v1 is one synchronous subagent per call over a shared worktree.
  Concurrent or nested subagents (and the commit/push races they'd cause) are explicitly out of scope.
- **Session checkpoint summarization is lossy.** F2's compaction trades fidelity for budget; bound it
  and keep the full pre-checkpoint messages in `agent_sessions` (F1) so nothing is truly lost.
