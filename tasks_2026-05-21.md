## Bugfix: Agent goes offline due to tight heartbeat timeout + no retry on failure

**Root cause (two parts):**

1. Offline threshold = `HeartbeatIntervalSec × 2 = 60s`. With heartbeats every 30s this gives zero tolerance — one late or failed heartbeat and the agent is offline within the next maintenance tick (15s).
2. `heartbeatLoop` in `agent/agent.go` logs errors and waits the full 30s before retrying. A single transient failure creates a 60s gap, which equals the threshold.

**Fix A — `server/server.go`:** Change multiplier `×2` → `×3` (90s threshold, survives one missed heartbeat):
```go
n, err := s.db.MarkOfflineAgents(ctx, s.cfg.Agents.HeartbeatIntervalSec*3)
```

**Fix B — `agent/agent.go`:** Add a quick retry on heartbeat failure so a transient error doesn't create a full 30s gap.

**Note on re-registration logs:** "Agent re-registered" is expected — agents re-register by name on every process startup because their records persist in the DB. The server correctly updates them to `online`. Not a bug, just informational.

## Bugfix: `tasks/next` does not atomically claim tasks — causes infinite "Task updated" log spam

**Root cause:** `GET /api/agents/{id}/tasks/next` calls `GetNextTask` (read-only SELECT) then immediately `prepareClaimResponse`, which writes `StartedAt` + workspace fields back via `UpdateTask`. But it **never calls `ClaimTask`**, so the task's `status` stays `BACKLOG` and `assigned_agent_id` stays empty. On every subsequent agent poll, `GetNextTask` returns the same task again → `prepareClaimResponse` runs again → `UpdateTask` → "Task updated" log. Repeats until the server is restarted or the task is claimed some other way.

The explicit `/api/tasks/{id}/claim` endpoint correctly calls `ClaimTask` (atomic tx: status → DEVELOPING, agent assigned) before `prepareClaimResponse`. `tasks/next` was missing this step.

**Fix — `server/handlers.go`, the `tasks/next` block (~line 753):**

Replace:
```go
claimResp := s.prepareClaimResponse(r.Context(), task, agentID)
api.WriteJSON(w, http.StatusOK, claimResp)
```

With:
```go
if err := s.db.ClaimTask(r.Context(), task.ID, agentID); err != nil {
    // Another agent may have raced us — return nil so the agent retries
    api.WriteJSON(w, http.StatusOK, nil)
    return
}
task, _ = s.db.GetTask(r.Context(), task.ID)
claimResp := s.prepareClaimResponse(r.Context(), task, agentID)
api.WriteJSON(w, http.StatusOK, claimResp)
```

## Feature: Delete Logs

Allow users to delete logs from the UI. The app has three log types exposed on the Logs page:

| Log type | Storage | Current endpoints |
|---|---|---|
| System logs | `logs` table (main DB) | `GET/POST /api/logs` |
| Agent logs | `agent_logs_YYYY_MM` partitioned tables (LogDB) | `GET /api/agent-logs` |
| Task logs | `task_logs_YYYY_MM` partitioned tables (LogDB) | `GET /api/task-logs` |
| Chat log | view over `messages` table (main DB) | `GET /api/chat-log` |

**Scope:** Bulk delete (clear all, or clear before a given date). No per-row delete — the UI has no row selection and individual log entries are not actionable records.

**Note on chat log:** The chat log is a read-only view over the `messages` table (LLM conversation history). Deleting those records would remove data used for conversation context. **Exclude chat log from delete scope** — it is not a log in the operational sense, and deleting messages has wider side effects.
